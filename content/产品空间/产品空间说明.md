## 这里放什么

产品空间保存**项目为什么做、做到什么程度**：

- 需求背景、目标与范围；
- 验收标准与优先级；
- 产品决策与取舍原因；
- 不做什么，以及为什么不做。

## 不放什么

- 界面细节与组件实现 → 设计空间；
- 接口、数据与架构 → 技术空间；
- 测试执行记录 → 测试空间；
- 排期承诺与个人任务清单 → 任务记录，而不是知识文档。

## 建议结构

一篇需求文档至少包含：

1. 背景：问题从哪来，谁受影响；
2. 目标：完成后可以观察到什么变化；
3. 范围：包含什么，明确不包含什么；
4. 验收标准：可复现、可观察的结果；
5. 依赖与风险；
6. 状态：已确认 / 待评审 / 待验证。

产品决策单独成文，写清选项、结论与原因，避免只留下结论。

## 写作要点

- 验收标准描述行为，不写「功能正常」这类无法验证的话；
- 需求变更必须留下原因和影响范围；
- 状态改变时更新 `updated`；
- 引用其他分类时写明标题，不复制整段内容。

## Agent 指引

- 做设计与开发前，先读本分类的当前维护资料；
- 需求与设计冲突时，回到产品确认，不在实现层自行改范围；
- 没有验收标准的需求，不直接进入实现；
- 任务结束后，把新的产品结论补回本分类，而不是只留在会话里。
